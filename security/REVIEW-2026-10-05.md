# Solana security review — 2026-10-05

Reviewed baseline `69d3e6b`, then changed local source only. No public deployment,
authority transfer, fee change or real payment was made in this review.

## Confirmed findings and fixes

| Finding | Reproduction before fix | Root-cause correction |
| --- | --- | --- |
| Unauthorized first-config takeover | Local validator accepted outsider initialization; assertion `expected failure with Unauthorized` failed and config tests then failed because the outsider held authority. | Bind initialization to this executable's actual ProgramData upgrade authority. Validate executable identity, ProgramData relationship and signer. |
| Collector can deny SPL sweeps by changing ATA authority | After the first fix, 39 tests passed and the new collector-owner-change test failed with `ConstraintTokenOwner` before handler execution. | Pin the canonical collector ATA address, move its mutable state validation into the handler, and redirect undeliverable fees to settlement. |

Both regressions were written and executed before their corresponding logic
change. The final local validator run passed **41 tests, zero failures** in
93 seconds. This includes substitute-program/ProgramData rejection, ordinary
token and SOL settlement, exact fees, rounding, roles, wrong destination
rejection, closed/recreated ATAs, fixed terms, frozen collector redirection,
and collector ATA-authority redirection. Five host unit tests and strict
Clippy (`-D warnings`) also passed; TypeScript and test formatting passed.

Used Agave 2.1.21, platform-tools v1.43 (SBF rustc 1.79), pinned Cargo.lock,
Anchor JS/CLI 0.31.1 and locked Anchor Rust crates 0.31.2. The baseline generated
IDL exactly matched the server's checked-in IDL before source changes.

Candidate `target/deploy/recvfund.so` after both fixes: **375512 bytes**, SHA-256
`fbaa37f5956afad510456d62238fc99601e863c2dbdef730bd791c9d35803298`.
This is a **local candidate**, not the public devnet binary. Build paths/tooling
can affect the Solana binary: run a verified release build before replacing
deployment provenance. Existing config and merchant layouts and sweep account
positions are unchanged; initialization adds `program` and `program_data`.

The Anchor 0.31.1 CLI IDL command failed reproducibly on Rust 1.85.1 and 1.90
because it injects `procmacro2_semver_exempt`. The official locked
`anchor-lang-idl` 0.1.4 compiler generates the IDL successfully without that
obsolete flag. `tools/idl-build` invokes that upstream compiler directly;
`scripts/build.sh` builds SBF, generates validated IDL and emits TS types.

The downloaded SDK's `syscalls.txt` is empty, so its post-build warning listed
standard Solana syscalls as unknown. Actual local-validator execution passed
all 41 tests, which exercises those runtime calls; the warning is not treated
as proof of either correctness or an exploitable program defect.

## Release blockers and follow-up

- The documented devnet program has not received these fixes. Existing config
  initialization is already complete there, but the collector ATA denial still
  matters for the old binary. Do not present source fixes as deployed protection.
- Server provenance and release IDL need an explicit candidate/deployment
  promotion workflow. Verify ProgramData authority and exact binary before
  permitting checkout. Initialization must precede authority revocation.
- Merchant PDAs remain globally keyed by merchant ID. Server setup must verify
  the recorded admin/destinations/fees to reject ID squatting. A seed migration
  would change all deposit addresses and is outside this compatible fix.
- Independent security audit, verified release build, funded devnet payment
  lifecycle, and production authority/key governance remain required.

Official references: [Anchor program and ProgramData constraints](https://github.com/coral-xyz/anchor/blob/v0.31.1/lang/src/accounts/program.rs),
[RustSec advisories](https://rustsec.org/advisories/),
[Solana verified builds](https://solana.com/docs/programs/verified-builds).

## CI/CD follow-up

The repository initially had zero GitHub workflows. A fresh archived checkout,
without a deployment program keypair, passed all 41 validator tests. This
confirmed the configured public program ID and disposable authority suffice
for local execution; no secret deployment material belongs in CI.

A repeat of cargo-audit 0.22.2 reproduced five yanked-index timeout errors while
returning exit code zero. The gate now uses cargo-audit for RustSec and a separate
exhaustive crates.io sparse-index scan for every locked registry package. The
scan validates exact version/checksum and non-yanked status, retries only network
errors, and fails if any result is missing. Regression tests cover unreviewed
advisories, missing versions, yanked rejection and an allowed version. The real
network scan passed for all **260 registry packages**, zero yanked packages,
zero vulnerabilities, and the same three explicitly reviewed warnings.

Read-only devnet inspection on 2026-10-05 confirmed ProgramData
`BPQjMEoaXC7J4ASpJj5NEvJGxRcdAamDxqsFL7335wV`, authority
`58tYVJZ3DadHLW7aA4gGAWNxS1dEkm6ifseFqZ4LyTcV`, and last deployment slot
`506820396`. The 319568-byte program dump's first 312088 bytes matched the
server's supported SHA-256 `a5e3df7dd16d4d0f10aed47bb9f3e23a277e213aeac241dab0c7adc1a97f5ed4`;
all remaining bytes were zero. Neither the default CLI signer path nor the
previously documented `~/.recvfund/keys` directory exists on this machine.
Authority access has **not** been established; only public data was inspected.

Pinned PR/push security CI and manually dispatched candidate preparation now
exercise the checks and retain manifests/evidence. The manual workflow repeats
the Docker build from clean source and compares bytes, then inspects public
ProgramData without signing. A successful artifact build does not mean the
candidate has been deployed or that external audit/funded acceptance is complete.
See README for the artifact schema and separate promotion requirements.

The first complete hosted gate passed five host tests, strict Clippy, the six
release-tool regressions and the exhaustive dependency scan. It then correctly
rejected a dirty checkout before building: Corepack had inserted the missing
`packageManager` field into package.json during install. Pinning Yarn plus its
integrity hash in package.json fixes the input contract; the clean-tree guard
remains enforced.
